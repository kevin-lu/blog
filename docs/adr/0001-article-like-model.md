# ADR 0001: 点赞功能数据模型设计

## 状态

已接受

## 背景

Blog 项目需要添加文章点赞功能，让读者快速表达对文章的喜爱。需要设计合理的数据模型来存储点赞记录。

## 决策

### 1. 点赞数据存储方式

**决策**：使用独立的 `article_likes` 表存储点赞记录，而不是在文章表中添加 `like_count` 字段。

**理由**：
- 支持防重复点赞（同一用户只能点赞一次）
- 便于扩展（如点赞用户列表、点赞时间分析）
- 数据量小，实时计算性能可接受

### 2. 点赞计数策略

**决策**：实时计算点赞数（`COUNT(article_likes)`），不缓存到文章表字段。

**理由**：
- 当前文章数量和点赞数据量小
- 简化数据一致性维护（无需同步缓存）
- 查询频率不高，性能影响可忽略

### 3. 用户标识策略

**决策**：同时支持登录用户和未登录用户点赞。

- **登录用户**：使用 `user_id` 标识
- **未登录用户**：使用 `session_id` + `ip_address` 标识

**理由**：
- 降低点赞门槛，提升互动率
- 保留扩展能力（后续可要求登录）

### 4. 防重复约束

**决策**：使用数据库唯一约束防止重复点赞。

```sql
-- 登录用户唯一性
UNIQUE CONSTRAINT uq_article_user (article_id, user_id)

-- 未登录用户唯一性
UNIQUE CONSTRAINT uq_article_session (article_id, session_id)
```

## 权衡

### 正面影响

- ✅ 数据模型清晰，易于理解和维护
- ✅ 支持防重复点赞，数据一致性好
- ✅ 便于后续扩展（如点赞列表、分析功能）
- ✅ 实时计算避免缓存同步问题

### 负面影响

- ❌ 高并发场景下，实时计算可能成为瓶颈（但当前数据量小，可接受）
- ❌ 每次查询文章都需要 JOIN 或子查询获取点赞数（可通过后续缓存优化）

### 替代方案

#### 方案 A：缓存计数
在文章表添加 `like_count` 字段，点赞时同步更新。

**为什么不选**：
- 增加数据一致性复杂度
- 当前数据量小，无需过早优化
- 可以在性能问题时再添加

#### 方案 B：仅支持登录用户
只允许登录用户点赞。

**为什么不选**：
- 降低用户互动门槛
- 未登录用户体验更好
- 保留登录用户标识，便于后续升级

## 合规性

与现有项目架构一致：
- 使用 SQLAlchemy ORM（符合现有数据访问模式）
- 遵循项目命名约定（表名复数、类名单数）
- 复用现有 Flask-JWT 认证机制

## 备注

如果未来点赞数据量增长到百万级别，建议：
1. 添加 Redis 缓存点赞数
2. 使用异步队列更新计数
3. 考虑分表策略
